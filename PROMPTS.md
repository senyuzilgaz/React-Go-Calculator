# Prompts

Record of the prompts used to produce this project, grouped by session. Prompts are reproduced
**verbatim**, including typos, since the point of the record is what was actually asked.

Sessions are appended in the order they ran. Each session notes the agent used and what it
produced.

**On timestamps.** Times are local (UTC+03) and taken from the modification times of the
artifacts each turn produced. Where a turn produced no artifact that still carries its original
mtime, the time is given as a bounded range rather than a precise value, and marked as such.

### 1 — Architecture and decision log

*2026-09-20, between 16:38 and 17:13 (repo created at 16:38; bounded by the first timestamped
artifact)*

```text
We are going to design full stack calculator application with typescript and react frontend and go backend microservices. Frontend will consume backend go api to perform arithmetic operations addition, substraction, multiplication, division, exponentiation, square root and percentage.

Frontend should be intuitive for entering input and design with proper input validation and error handling and responsive in design to support basic mobile applications.

Backend should be rest api implemented with go to expose the necessary operations.

Before starting implementing anything I want to create te architecture and write it down with you dont generate any implementation just give me the decisions that will shape this codebase and for each please provide the tradeoff realistic options and your recommendation with rationale. Im specifically unsure about the floating point precision in the calculator operations. This is 3-4 hours of excercise judged on clarity and maintabiibility so please mentipn anything that you can be overengineering for us.

Then lets create docs/DECISIONS.md and record the deisions accepted here onward as these are important and we will later use to create readme. this decisions file should be append only and new entries added but old ones should not be changed
```

**Outcome:** Thirteen architecture decisions presented with options, trade-offs, and
recommendations, plus an explicit list of what would be overengineering at this scope. Four
decisions were identified as the user's to make and put back as questions.

### 2 — Decisions selected

*2026-09-20, between 16:38 and 17:13 (bounded; answers to the four questions above)*

```text
D1 — Service topology:
One backend go service is enough for now

D2 — API shape:
I want one endpoint per operation, POST /api/v1/operations/{op} but also a get endpoint to discover the operations: GET /api/v1/operations that should return operation catalog name, parameters symbol etc

D3 — Floating point precision:
float64 with rounding policy soudns the simplest for now but this rounding policy should be documented

D9 — Frontend interaction model:
Keypad with reduced state meachine sounds good, there should be definitely NO CLIENT SIDE arithmetic at all
```

**Outcome:** `docs/DECISIONS.md` created with ADR-0001 – ADR-0013, append-only, each entry
carrying Context / Decision / Alternatives considered / Consequences.

### 3 — Failure modes and API contract

*2026-09-20, ~17:13 (`api/openapi.yaml`)*

```text
Just wanted to confirm, we are documenting every failure mode right, 400 for malformed body or wong parameters, 404 for unknown operation like you mentioned but also 422 for mathmatically undefined results like divide by zero sqrt of neg overflow etc? Lets also write api/openapi.yaml as the complete contract of this api before starting to implement either side
```

**Outcome:** `api/openapi.yaml` written (OpenAPI 3.1.0, validated, all `$ref`s resolve).
`405 METHOD_NOT_ALLOWED` added to the taxonomy, since Go's `ServeMux` emits it automatically.
ADR-0014 appended.

### 4 — Verified examples
